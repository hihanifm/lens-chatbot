Problem & Solution

What is it?

The Problem

  • Debugging complex bugs means juggling tracker details, huge log files, and scattered team knowledge
  • Engineers re-derive the same root causes that colleagues already solved
  • Logs are big — reading them manually takes hours
  • Context is lost when the session ends
  • No easy way for teammates to jump in and help
Without Lens
grep logs manually → jira tab → slack for context → repeat next week

The Solution

  • One place to load a bug — tracker details fetched automatically
  • Upload / download log attachments, browse zip contents without extracting
  • AI agent reads the files and answers questions in natural language
  • Discoveries saved to a shared troubleshooting wiki (Karpathy-style)
  • Multiple engineers can join the same session in real time
With Lens
load bug → agent reads logs → answer in seconds → wiki auto-updated

Steps 1–2: Bug Context

  • POST /session {bugId}
  • Tracker returns title, description, comments, attachments
  • Workspace created at DATA_DIR/workspaces/BUG-ID/
  • bug.json + bug_summary.md written

Step 3: Files

  • File Explorer shows available attachments
  • Zips browsable without extraction (lazy)
  • User selects files for agent scope
  • Comment context auto-injected into prompt

Steps 4–5: Intelligence

  • Agent reads wiki index first (mandatory)
  • Streams answer token-by-token via SSE
  • Multi-turn follow-ups reuse ClineCore session
  • User clicks "Save to Wiki" after resolution

One Session Per Bug

  • Bug ID is the natural room key
  • All engineers share the same session for a given bug
  • Messages have user_name column — attribution preserved
  • Re-loading a bug returns existing session + history
GET /session/:id returns session, bug details, and full message history in one call.

Workspace Isolation

  • Each bug gets its own directory under DATA_DIR/workspaces/
  • bug.json never modified after creation
  • bug_summary.md formatted for agent consumption
  • Agent can write to agent_notes/ (sandboxed)
All paths validated against session workspace root — traversal attack prevention.

Intelligence Layer

Agent & Skills System

ClineCore Configuration

  • Mode: plan — read-only analysis, no file editing
  • Disabled: APPLY_PATCH, EDITOR, FETCH_WEB_CONTENT
  • Max iterations: 12 (configurable via AGENT_MAX_ITERATIONS)
  • LLM provider: Ollama / OpenAI / OpenAI-compatible
  • Single shared instance across all sessions

Available Agent Tools

bash/sh python3 ripgrep jq grep awk sed find cut sort
All available in Docker. Agent shells out freely — it can write Python one-liners, search logs with ripgrep patterns, or use jq for JSON parsing.

Skills System

  • Skills are Cline-format markdown files (YAML frontmatter + body)
  • SKILLS_DIR: colon-separated paths — e.g. /app/skills:/mnt/team-skills
  • All skill files passed to agent prompt — agent decides relevance
  • No backend keyword-matching logic (LLM-first principle)

Comment Context Injection

  • Bug tracker comments mapped to file references
  • When file is selected, relevant comments appended to prompt
  • buildFileCommentMap() in agentPrompt.ts
  • Agent sees: Comment: "User reported crash at..."
  • No extra API calls — comments already in bug.json

Lazy Zip Extraction (Phase 2)

  • Zips NOT auto-extracted on download
  • GET /zip-contents reads central directory only — instant, no extraction
  • POST /extract-file extracts one entry at a time on demand
  • Minimal disk usage — user controls what lands on disk
  • Traversal-safe: all paths validated against workspace root

File Selection → Agent Scope

  • Selected files stored in sessions.selected_files (JSON array)
  • Persists across page refresh and multi-user joins
  • Agent prompt lists only selected files in scope section
  • Agent is instructed to read files before answering (enforced)
Endpoints: GET /workspace/files (tree) · POST /extract-file · GET /attachment/download
Feature Deep Dive

Multi-user Collaboration

Bug ID = Room

  • One session per bug — all engineers join the same room
  • Messages have user_name for attribution
  • Full history visible to all participants
  • Analysis stream broadcast to all connected clients

Auth (Name + PIN)

  • POST /auth — register (new name) or login (existing)
  • PIN hashed with scrypt, stored in SQLite
  • UUID assigned on registration, stored in localStorage
  • Identity persists across sessions and page refreshes
  • GET /users/:id — fetch profile by UUID

Presence Room (broadcast.ts)

  • 25-second keepalive ping per client
  • addClient / removeClient / broadcast
  • Clients auto-removed on connection close

SSE Event Streams

GET /session/:id/analyze
Active analysis stream — emits text, status, done, error events as the agent works. One per running analysis.
GET /session/:id/listen
Passive observer stream — receives all broadcast events plus presence events:
presence:snapshot presence:join presence:leave
Transparency principle: every meaningful internal state change emits as a status event in the stream. Engineers see the full agent lifecycle — tool calls, file reads, reasoning steps.

Agent Mandatory Enforcement

  • Agent prompt includes wiki root index path
  • System prompt uses "MUST" language — read wiki before analysis
  • Three-step navigation: root → module → entry
  • Prevents re-deriving known root causes
  • Environment.md also reinforces wiki consultation

REST API

  • POST /session/:id/wiki — synthesize + save entry
  • GET /wiki — list all entries
  • GET /wiki/:module — entries in module
  • GET /wiki/:module/:filename — read full entry
Synthesis is a non-streaming LLM call via wikiService.ts. Index files updated automatically on every save. Collision-safe filenames: YYYYMMDD-BUGID-slug.md

Why Two Levels?

Root index gives a module-level map. Module index gives a summary-level view. Agent never scans hundreds of files — it navigates like a human would read a well-organized wiki.

Engineering Philosophy

Key Design Decisions

🔌

Interface-based Backends

AgentRunner and BugTracker are TypeScript interfaces. Swapping implementations is one line in index.ts. Product code never imports @cline/sdk directly — only ClineCoreAgentRunner does.

🧠

LLM-first Principle

Skill selection, response format, wiki navigation — delegated to the model. Backend only handles I/O, persistence, streaming, and auth. No keyword-matching, no response templating, no hard-coded skill routing.

📡

Transparency — Show Everything

This is an engineer's tool. Every agent lifecycle event surfaces as a status SSE event. Unknown Cline SDK events pass through as · event.type. Engineers see the full reasoning process, not just the final answer.

💤

Lazy / On-demand I/O

Zip files not extracted until the user explicitly selects individual entries. Wiki not synthesized unless the user requests it. Disk usage stays minimal; nothing happens until it needs to.

Database
node:sqlite — built-in Node 22, no native addon needed. Sufficient for session + message storage.
Transport
SSE over WebSocket — simpler, HTTP-native, firewall-friendly, proxy-compatible.
Skills
Markdown files — portable, version-controlled, LLM-parseable, admin-editable without code changes.
